# 0.3 — проверка прямого HTTP MPEG-TS по фактическому Sink UE32H6300

Пользователь передал GetProtocolInfo Sink: есть `video/mpeg:*` и
`video/mpeg:DLNA.ORG_PN=AVC_TS_MP_HD_AAC_ISO`, HLS в переданном фрагменте нет.
Ошибка TV «файл не поддерживается» на 0.2.2 не устанавливает, проверял ли TV
MIME, контейнер или сам поток. В 0.2.2 TS-тест рекламировался как video/mp2t,
которого нет в присланном списке.

Изменения:
- Конечный TS-тест объявляется video/mpeg и в HTTP, и в DIDL protocolInfo.
- Основной live transport — прямой HTTP MPEG-TS video/mpeg, без HLS-плейлиста.
- HLS сохранён отдельным переключаемым режимом.
- Поток выдаётся завершёнными MPEG-TS-сегментами по одному соединению, начиная
  с последнего полного сегмента с PAT/PMT и IDR. Длина неизвестна; Content-Length
  не выдумывается, Transfer-Encoding chunked не добавляется. HTTP-ответ завершается
  закрытием соединения. Это допустимое HTTP framing, но поддержка Samsung не доказана.
- Live Range=bytes=0- допускается как обычный GET; другие Range возвращают 416.
- Каждая подписка удаляется при закрытии соединения. Очередь на клиента <=2 МБ,
  при медленном чтении соединение закрывается, чтобы не исчерпать память ReplayKit.
- Журнал host app получает последние HTTP-запросы TV из status endpoint расширения.
- Код не объявляет полное соответствие именованному DLNA profile: только MIME,
  который renderer действительно объявил с wildcard.

Проверки здесь: синтаксический разбор Swift, plist, Xcode-проект и все пути к файлам.
Добавлены regression cases подписки/порядка данных/отписки. Их запуск и Apple SDK
сборка требуют Mac; они здесь не выполнялись. Работа на Samsung не подтверждена.
