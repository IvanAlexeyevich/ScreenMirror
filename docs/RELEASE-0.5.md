# 0.5.0 (8) — сохранение, подключение, интерфейс и подача TS

## Что реализовано

1. Адрес, имя, UDN и последний выбранный телевизор хранятся в атомарном JSON в
   Application Support. При запуске сохранённый TV проверяется обычным HTTP и
   появляется без повторного ввода URL. UDN сохраняет идентичность при смене IP,
   если новое описание найдено поиском. Сохранение работает при обновлении поверх
   приложения с тем же Bundle Identifier; удаление приложения удаляет и его данные.
2. Обнаружение сначала пытается SSDP multicast, затем посылает directed M-SEARCH
   по текущей IPv4 Wi-Fi-подсети (не более локального /24). Unicast не требует
   multicast entitlement, но требует local-network permission и ответа TV именно
   на unicast. Это не гарантировано для каждой прошивки Samsung. Подсети крупнее
   /24, IPv6-only и client isolation автоматически не решаются.
3. Для первого подключения без набора адреса есть QR-сканер и tools/Pair-TV.py.
   Помощник на Mac ищет TV по стандартному SSDP и создаёт/открывает QR на рабочем
   столе с помощью Core Image. iPhone считывает его, проверяет настоящее описание
   по HTTP и сохраняет устройство. Настройки TV не меняются, код не размещается
   на внешнем сервере. Помощник и камера здесь не испытаны на macOS/iPhone.
4. Качество, FPS, битрейт, звук, reconnect, транспорт, коррекция альбомного поворота
   и ровная подача сохраняются автоматически. При чтении старого JSON отсутствующие
   поля получают значения по умолчанию. Ошибочные FPS/битрейт/режим нормализуются.
5. Главный экран: карточка TV, основная кнопка запуска, системное подтверждение,
   остановка и краткие параметры. Настройки, диагностика и тестовый тон вынесены
   отдельно; ручной URL спрятан в расширенные способы подключения. Никаких
   поддельных состояний успешного воспроизведения: «захват активен» обозначает
   ответ расширения, а доступность TV — получение реального device description.
6. Прямой TS по-прежнему отдаётся без HLS сегментного ожидания. Добавлен pacer с
   шагом 20 мс: MPEG-TS null packets заполняют паузы, например когда статический
   экран сжимается в очень маленький поток. Это проверяет гипотезу byte-based
   буферизации TV, не меняя кодированные H.264/AAC. Качество и выбранный битрейт
   энкодера не снижаются. Транспортная скорость примерно 1.25 * bitrate + 192 кбит/с,
   поэтому растёт Wi-Fi трафик. Настройку можно отключить для сравнения.
   Опционально аппаратному энкодеру предложен MaxFrameDelayCount=0; неподдержка
   этого свойства логируется и не ломает запуск.

## Что действительно проверено

В этой среде установлен и запущен Swift 6.0.3 для Linux, а не только parser.

- **13 XCTest tests, 0 failures, 0 skipped.** Production Swift для JSON сохранения
  компилируется и выполняется. Проверены новый экземпляр хранилища, все настройки,
  адрес/выбор TV, 50 последовательных атомарных перезаписей, отсутствие файла,
  повреждённый JSON, неизвестная версия и миграция недостающих полей.
- Production SSDPProbe проверен настоящим UDP на loopback: M-SEARCH, реальный
  сокет/ответ и устранение повторов. HTTP device description и SOAP Play/Stop/state/
  GetProtocolInfo проверены реальными HTTP-запросами к Python mock renderer,
  включая relative controlURL, namespace XML, escaping DIDL и SOAP fault.
  **Mock renderer не является телевизором Samsung.**
- FrameSchedule, LiveStreamBuffer и TSPacketPacer исполняются в тестах: монотонность,
  IDR, bounded cache, пропуск данных до IDR, границы GOP, ровная скорость и
  неизменность медиапакетов.
- Отдельный production MPEG-TS mux harness с реальными H.264/AAC скомпилирован
  swiftc и запущен. FFmpeg декодировал 360 кадров / 564 AAC packets без ошибок.
  Проверка framemd5 видео и аудио до и после pacer совпала побайтно. Таким образом
  новый transport pacing не ухудшает качество тестового медиасодержимого.
- Swift parser для iOS-only файлов, plist, Xcode-проект и ссылки на файлы проверены.

Логи сохранены в docs/test-results/. Для воспроизведения тестов:

```sh
python3 tools/run_tests.py
bash tools/test_mux.sh
```

## Что ещё не проверено и не гарантируется

Нет доступа к Xcode, iPhone или домашнему Samsung. Поэтому здесь не выполнены
Apple SDK typecheck / simulator build, UI/camera tests, code signing и испытания
нового unicast SSDP на прошивке TV. Для macOS добавлены CI и
`bash tools/verify_on_mac.sh`, выполняющий настоящую iOS simulator-сборку и тесты.
Этот macOS шаг здесь не запускался. Исполняемые Linux tests не подменяют его.

End-to-end задержка 0.5 на телевизоре **не измерена**. Нельзя обещать устранение
8–15 секунд или отсутствие всех проблем после установки. Samsung может держать
собственный буфер, настройка которого не предоставляется через AVTransport.
Pacer может уменьшить byte-based ожидание при малоподвижном экране, но может и
не повлиять на фиксированный временной буфер. Проверять нужно оба режима с одним
качеством/битрейтом, сравнивая секундомер на iPhone и TV через 30–60 секунд.

## Установка и первая проверка

1. Остановите активный broadcast; установите через Xcode поверх, с прежним Bundle ID.
2. Убедитесь в версии 0.5.0 (8). Старые версии не сохраняли параметры, поэтому
   перенести их из них автоматически невозможно: выберите их один раз в 0.5.
3. Нажмите «Найти телевизор». Если directed SSDP не поддержан, используйте QR из
   помощника Mac или один раз сохраните ранее известный URL вручную.
4. Закройте и снова откройте приложение: устройство и настройки должны восстановиться.
5. Сравните задержку с включённой/выключенной «Ровной подачей потока» в новых сеансах.
   При неизменной задержке экспортируйте журнал с очередью HTTP и pacer.
