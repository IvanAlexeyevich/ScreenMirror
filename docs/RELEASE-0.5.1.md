# 0.5.1 (9) — устойчивость выдачи и восстановление TV

## Основание

Пользователь сообщил о сетевой плашке TV, разрывах и задержке около 20 секунд.
На скриншоте ReplayKit явно завершён ошибкой «Энкодер выдаёт поток быстрее
выбранного темпа». В 0.5 эта проверка вызывала finishBroadcastWithError через
pipeline.onError, после чего сервер закрывался. Это подтверждённый программный
источник одного вида разрыва, но не доказательство причин всех сетевых ошибок.

## Исправления

- TSPacketPacer рассчитывает объём по прошедшему монотонному времени, а не числу
  вызовов таймера. Dispatch timer может объединять события при загрузке media queue.
- LivePacingController не допускает накопления очереди подачи на многие секунды:
  при превышении 0,5 секунды целевого потока или задержке таймера >250 мс с данными
  в очереди автоматически переходит на прямую выдачу до конца сеанса.
- При переходе сохраняет ВСЕ ещё не выданные медиабайты, их порядок и признак начала
  GOP, включая частично выданный PES. Нет принудительной остановки ReplayKit,
  пропуска кодированных кадров или снижения разрешения/битрейта из-за этой ошибки.
- HTTP status больше не делает queue.sync на media queue: маленький snapshot под
  NSLock обновляется со стороны энкодера. Запрос статистики не задерживает выдачу
  потока во время Core Image render.
- TCP noDelay и keepalive включены. Считаются реальные читатели потока, закрытия,
  время успешной передачи данных в сетевой стек и очередь записи. Завершение
  contentProcessed не является подтверждением показа картинки телевизором.
- Повторное подключение TV проверяется каждые 2 секунды. Потерянный HTTP reader
  может восстанавливаться даже при AVTransport=PLAYING. Защита cooldown 15 секунд
  предотвращает непрерывные Stop/Play во время обычной буферизации. Новый URI с
  query session получает текущий GOP/IDR. Возможна короткая пауза воспроизведения.
- Последовательные ошибки SOAP/сети больше не завершают здоровый ReplayKit-сеанс
  после шестой попытки. Retry с backoff продолжается, пока пользователь не остановит
  сеанс. Системно остановленный iOS broadcast автоматически не перезапускается.
- HTTP и DIDL для live TS объявляют sender-paced + streaming: флаги 0x81000000,
  no seek. В присланном Sink TV присутствовали 0xED100000, включая эти биты.
  Не заявляется именованный DLNA codec profile или полная сертификация DLNA.
  Семантика битов сверена с публичным gupnp-av/gupnp-dlna.h:
  https://github.com/GNOME/gupnp-av/blob/master/libgupnp-av/gupnp-dlna.h
  Код библиотеки в приложение не включён. Эти метаданные могут помочь классифицировать
  live-поток, но их влияние на буфер Samsung не измерено.
- Диагностика дополнена режимом выдачи, причиной auto-bypass, очередью capture,
  A/V timestamp offset при свежем аудио и количеством HTTP-разрывов.
- Основной интерфейс и сохранённые настройки не изменены. Исправления macOS 12
  в Package.swift и iOS 17.4 availability для энкодера сохранены.

## Исполненные проверки

20 XCTest tests проходят на Swift 6.0.3 Linux без ошибок и пропусков. Новые cases:
coalesced timers 40/100 мс, нерегулярный таймер, трёхсекундный stall, превышение
темпа, переход с частично отправленного PES, потеря reader при PLAYING, cooldown
и отсутствие ложного restart на паузе/при первом запуске.

Production TS harness с реальными H.264/AAC проверяет также реальный переход
paced → direct с частичным PES. FFmpeg декодирует 360 кадров / 564 AAC packets;
framemd5 аудио и видео совпадают для прямой выдачи, paced и overflow fallback.
Это доказывает сохранность тестового media, не отсутствие всех аппаратных проблем.

Workflow ветки codex/stream-stability-051 выполняет те же тесты на macOS, собирает
настоящий unsigned iphoneos arm64 IPA и проверяет вложенный Broadcast.appex.
Результат Apple SDK сборки и артефакт смотрите в GitHub Actions для нужного commit.

## Задержка и практические пределы

20 секунд end-to-end на конкретном Samsung здесь не измерены. Известная очередь
подачи теперь ограничена 0,5 секунды перед bypass; HTTP buffer остаётся ограниченным
и при реальном медленном reader может закрыться с последующим recovery.
Плашка сети при настоящем разрыве Wi-Fi или перегрузке TV полностью не исключена.

Если pacingBytes=0, captureQueueMs малы, HTTP queue мала, A/V PTS близки, но картинка
по секундомеру отстаёт на 20 секунд, причина может быть дальше по тракту — в буфере
телевизора/плеера. Публичная настройка размера этого буфера через AVTransport
не обнаружена. Sender-paced метаданные — проверяемая гипотеза, не гарантия
Miracast-подобной задержки. Подтверждение требует прогона реального iPhone/TV.

Для проверки используйте тот же bitrate/resolution, что в 0.5, минимум 10 минут
динамичного видео со звуком, переключения приложений и сравнение секундомера.
При оставшейся задержке экспортируйте журнал через 30–60 секунд после старта.
